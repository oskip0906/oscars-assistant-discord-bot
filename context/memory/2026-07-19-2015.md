If I just say, "Improve the search functionality," the agent might spend an hour rewriting the entire search indexer (over-engineering) or just adding a few keywords (under-engineering).

By saying, "Improve the search functionality to support fuzzy matching on usernames without increasing the query latency beyond 300ms," I’ve locked the scope. The agent now knows exactly what to focus on, which drastically reduces the chance of it "wandering off" into irrelevant parts of the codebase.

### 2. The Power of Testable Criteria
The secret weapon in this "Goldilocks Zone" is the **Acceptance Criteria**. By making these specific and testable (e.g., "The API should return a 404 for non-existent IDs," or "The new endpoint must be accessible via the existing Auth middleware"), I give the agent a way to "self-correct."

If the agent can mentally (or via its own internal test-running steps) check its work against those criteria, it’s much more likely to get it right on the first try. It’s the difference between a chef being told to "make it taste good" (subjective) and "make it spicy, salty, and served in a bowl" (objective).
